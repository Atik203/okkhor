Scope: integrate the seven sprint branches into `main` in a safe order, with
explicit conflict handling, interface verification, gates, and worktree cleanup.

not push, merge, open PRs, or edit GitHub.

## 1. Exact merge order

Order is chosen so the blocking contract lands first, independent 0.2 evidence
closes out next, new crates land one at a time so the shared `Cargo.toml` conflict
is small and isolated, and the review record lands last as the final audit
artifact. Review *work* is a pre-merge gate for every reviewed branch even though
the review report *branch* is merged last (see Section 5).

| # | Branch | Why here | Precondition |
| - | ------ | -------- | ------------ |
| 1 | `sdd/0.3-architect` | Blocking prerequisite: fixes public types, error types, dependency direction, integration points. Tasks 1-3 must not be validated against anything else. | Contract docs exist at the exact paths; ADR 0010 numbered and linked. |
| 2 | `docs/0.2-qa` | Independent 0.2 QA evidence; disjoint path (`docs/qa/0.2-matrix.md`). | Task 7 review clean; synthetic-only evidence; no real user text in matrix. |
| 3 | `docs/0.2-perf` | Independent 0.2 performance evidence; disjoint path (`docs/performance.md`). | Task 7 review clean; reproducible numbers only; consistent with QA matrix limitations. |
| 4 | `feat/0.3-lang` | First new crate; establishes the `okkhor-core`-only type usage other crates are checked against. | Contract landed (#1); Task 6 review clean; interface checks pass. |
| 5 | `feat/0.3-translit` | No dependency on `okkhor-lang`; lands second so the `Cargo.toml` member conflict is resolved incrementally. | Contract landed (#1); Task 6 review clean; interface checks pass. |
| 6 | `feat/0.3-compat` | FFI/security boundary; highest scrutiny, so it lands last among code crates. | Contract landed (#1); compat-specific security review clean; no real DLL load in tests. |
| 7 | `sdd/0.3-review` | Final audit record describing the integrated state and sign-offs. | All findings in the report resolved by owning agents; report reflects post-fix state. |

Notes on the order:

- Steps 2 and 3 are content-independent of step 1 in code terms, but keeping
  them after the architect commit means `main` always carries the contract before
  any 0.3 content. The two docs branches are mutually disjoint; if their merge
  order is swapped, re-check `docs/README.md` only.
- Steps 4-6 must each be merged with a fresh `Cargo.toml` resolution and a
  regenerated `Cargo.lock`. Do not batch all three crates into one conflict
  resolution pass.
- Step 7 is merged last deliberately: a report that says "finding open" must not
  coexist with a branch that was merged with that finding unresolved. If the lead
  prefers the gate evidence to be in `main` before the reviewed merges, the
  review branch may be merged immediately after step 1 **only if** its report is
  already in final "all findings resolved" state. Record whichever choice is made
  in the sprint ledger.

## 2. Conflict risks and resolution

### 2.1 Root `Cargo.toml` (highest risk)

Each of the three code branches is allowed exactly one new line in
`[workspace] members` (currently lines 3-10, a `crates/` alphabetical block):

- `feat/0.3-lang` -> `"crates/okkhor-lang"`
- `feat/0.3-translit` -> `"crates/okkhor-translit"` (crate name per plan:
  `okkhor-transliterate`; use the directory declared by the branch)
- `feat/0.3-compat` -> `"crates/okkhor-compat"`

Risk:

- All three insert into the same list at the same location, so the first merge
  is clean and the next two conflict in the `members` block.
- Less expected but still possible: `[workspace.dependencies]` changes or new
  external dependencies (notably `libloading`-style FFI loading in compat), plus
  `Cargo.lock` churn. The ledger ruling forbids cross-deps, so no new
  workspace-dependency line for a new internal crate should appear; if one does,
  stop and check it against the contract's dependency direction.
- Verify the exact crate directory name against the contract before accepting a
  member line; plan text uses `okkhor-transliterate` for the crate while the
  branch is named `feat/0.3-translit`.

Resolution rules:

1. Keep **all** three member lines; never drop one to "fix" a conflict.
2. Order the `crates/` entries alphabetically to match the existing block
   (`compat`, `core`, `lang`, `learn`, `storage`, `transliterate`, `win`),
   adjusting to the actual directory names.
3. Re-run `cargo check --workspace` after each resolution so `Cargo.lock`
   regenerates; then run `cargo test --workspace --locked`. Investigate any
   unexpected new dependency (AGENTS rule 8: reason + license check; no
   GPL/AGPL/non-commercial additions without owner approval).
4. Confirm no added crate is missing an ADR entry (AGENTS rule 9); ADR 0010 or
   ADR 0001 must cover the new crates.

### 2.2 Docs indexes

- `docs/adr/README.md`: the architect branch adds the ADR 0010 row (0001-0009
  already present). Add the row, do not rewrite existing rows. If ADR 0011 from
  Task 8 arrives on a branch outside this seven-branch set, merge its row
  separately and keep numbering/order monotonic.
- `docs/README.md`: currently links ADRs as a directory, not individual ADRs.
  Conflict arises only if a branch adds a top-level doc row (e.g., a design or
  review report). Resolution: keep every row, link once, no duplicate source of
  truth (AGENTS documentation rules).
- `docs/qa/README.md`: may gain a link if the QA matrix layout changes; Task 4
  owns `docs/qa/0.2-matrix.md`, Task 5 owns `docs/performance.md`.
- `docs/design/0.3-core-contracts.md` and `docs/adr/0010-core-contracts.md` are
  new files; low conflict risk, but check no other branch created `docs/design/`
  or reused ADR number 0010.
- Cross-doc consistency: QA matrix limitations (`LIM-01`, `LIM-02`, injected-path
  labels, p99 numbers) and `docs/performance.md` numbers must not contradict.
  Both branches must pass Task 7 review on evidence quality, privacy, and
  unsupported claims before merge.

### 2.3 Other shared-file watch items

- `Cargo.lock` is touched by every crate branch; regenerate, don't hand-edit.
- `AGENTS.md`, `docs/roadmap.md`, `docs/architecture.md` are not assigned to any
  branch. If a branch modifies them, flag it: scope control (AGENTS rule 9) and
  "update the relevant doc in the same change" must be reconciled by the lead.
- No branch should add real user text, proprietary bytes, or legacy executable
  paths. QA evidence stays outside git in the restricted share; only matrix text
  with `E-<row>-<sequence>` IDs is committed.

## 3. Interface checks from the architect contract

Source of truth: `docs/design/0.3-core-contracts.md` and
`docs/adr/0010-core-contracts.md` (Task A). Until `sdd/0.3-architect` is merged
these are unreadable here, so each item below is a **check to perform**, not a
confirmed result. Run these checks per crate branch at its merge step.

1. **Contract presence.** Both contract files exist at the exact paths, and
   ADR 0010 is linked from `docs/adr/README.md`. If absent, stop the merge.
2. **Public types.** `okkhor-lang`, `okkhor-transliterate`, and `okkhor-compat`
   use the candidate/layout/encoding types named in the contract from
   `okkhor-core`. No crate defines its own duplicate candidate struct. This
   applies the ledger ruling "all agents depend on `okkhor-core` types only; no
   cross-deps" and resolves the Task 1 / Task 2 duplicate-candidate risk.
3. **Error types.** Each crate exposes the error type specified by the contract
   and converts to/from the core error type as specified. No untyped string
   errors where the contract requires a typed error.
4. **Module dependency direction.** Check each new crate's `Cargo.toml`:
   - lang may depend on `okkhor-core` only;
   - transliterate may depend on `okkhor-core` only and **must not** depend on
     `okkhor-lang` (plan: "No dependency on `okkhor-lang`");
   - compat may depend on `okkhor-core` only and must not depend on lang or
     transliterate for its FFI boundary;
   - none of the three depends on `okkhor-win` for language policy; none adds a
     cross-dependency among themselves.
5. **Integration points.** Names and signatures exposed at the boundary match
   the contract exactly: the synthetic-fixture importer API (lang), the
   transliteration rule-engine and Bangla/English normalization helpers
   (transliterate), and the safe FFI adapter boundary with DLL path validation
   and per-adapter feature flags (compat). No invented public API and no
   renaming of public types without a contract/ADR update.
6. **Unsafe boundary.** `unsafe` appears only in `okkhor-win` and the explicitly
   reviewed compat FFI module; every unsafe block carries a `// SAFETY:` comment
   naming the invariant. `okkhor-core`, `okkhor-learn`, `okkhor-storage` remain
   `#![forbid(unsafe_code)]` (AGENTS rule 4).
7. **Compat test safety.** No test loads a real DLL or references the legacy
   folder `Nms Kontho x64 8.002`; DLL path validation is present; feature-flag
   names match the contract.
8. **Fixtures and privacy.** Only synthetic fixtures; no real user text in code,
   tests, or QA docs; no proprietary bytes committed (global constraints).
9. **Docs wired.** Contract and new-crate behavior are reflected in the relevant
   doc in the same change, with links rather than duplicated content.

Any failed check is a blocking review finding for the owning agent to fix on its
own branch; the lead does not fix code during merge (ledger ruling).

## 4. Required gates

Run on the integrated state after each merge, and again on final `main`. Gate
commands come from `AGENTS.md` (local Windows and CI contracts):

- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`, plus `cargo test --workspace --locked` for the CI
  contract
- `cargo run --package okkhor-daemon -- self-check` (must report `self-check: ok`
  and still demonstrate English, Bangla, transliteration, and persistence)
- `cargo check --workspace` after every `Cargo.toml` conflict resolution, to
  validate the regenerated `Cargo.lock`

Task/process gates:

- Task 6: one reviewer for lang/transliterate, one for compat/security boundary;
  both reviews clean with all findings resolved by the owning agent before each
  code branch merges.
- Task 7: QA matrix and performance-doc changes reviewed for evidence quality,
  privacy, and unsupported claims before steps 2-3 merge.
- PR policy (AGENTS): every PR links an existing issue (`Issue: #N` / `Refs #N`),
  CI green, no blocking review, squash-merge into `main`, delete branches, pull
  `main`, verify the resulting `main` CI run, close issues only after merge
  verification. The lead executes these; the manager only records the gate.
- Hot-path gate (AGENTS rule 7 / roadmap phase 2): local candidate generation
  p99 under 3 ms; any hot-path change needs before/after numbers. Task 5 supplies
  reproducible numbers; no regression averaged away.
- Global constraints: no real user text, no legacy executable run or copied
  bytes, synthetic QA fixtures only, Notepad select-all/delete before each inject
  test, statuses recorded as `DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` /
  `BLOCKED`.
- Dependency/license gate for any new crate or external dependency.

A branch that fails any gate stays open; do not merge to keep a green PR alive
(AGENTS: do not leave a green, reviewed PR open — but do not bypass a gate to
close it either).

## 5. Review-gate sequencing

The ledger rules that review gates happen before merge and that findings are
fixed by the owning agent, not the lead. Therefore, for each of branches 2-6:

1. Read the `sdd/0.3-review` report (from that worktree/branch) for the matching
   sign-off.
2. Confirm every listed finding is marked resolved by the owning agent.
3. Only then execute the merge step from Section 1.
4. Merge `sdd/0.3-review` itself last (step 7) as the final record, after its
   report has been updated to reflect the post-fix integrated state.

If the review branch cannot be read at merge time, treat that as `BLOCKED` for
the affected merge and record it in the ledger; do not assume a pass.

## 6. Worktree cleanup checklist

Cleanup is performed by the lead after verification, not by the manager.

- [ ] For every merged branch: confirm squash-merge into `main` and that the
      linked issue criteria are met before closing the issue.
- [ ] Confirm no uncommitted or untracked work remains in that worktree. In
      particular, this manager worktree's `docs/superpowers/` directory must be
      committed before its worktree is removed.
- [ ] Remove the worktree with `git worktree remove <path>`; use `--force` only
      with explicit owner confirmation.
- [ ] Delete the local branch with `git branch -d <branch>` (never `-D` on a
      branch whose merge was not verified).
- [ ] Delete the remote branch with `git push origin --delete <branch>` (lead
      only).
- [ ] Run `git worktree prune` and re-run `git worktree list` to confirm only the
      main `okkhor` worktree remains for this sprint.
- [ ] Do **not** remove worktrees for branches that were not merged or that have
      unresolved findings; leave them for the owning agent.
- [ ] Preserve reports in `E:\Nms_Kontho\akkhor-sdd-reports\` and the restricted
      QA evidence root outside git; cleanup must not delete evidence or reports.
- [ ] Leave the sibling directory `Nms Kontho x64 8.002` untouched (owner-provided
      legacy reference, not a worktree; never execute or modify it).
- [ ] Final verification on `main`: pull, re-run every gate in Section 4, confirm
      CI green, then update the milestone/ledger and close issues.
