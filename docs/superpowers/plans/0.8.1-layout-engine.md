the static-evidence record from the 0.8.1 audit. The approved design is
`docs/superpowers/specs/2026-11-24-fixed-layout-engine-design.md`; the tasks

## Static reference findings (2026-11-24)

All three reference keyboards genuinely switch tables at runtime; no reference
executable was launched, and no reference file was modified.

Conclusion: all three use a real, modifiable table and swap engine branches.
Okkhor 0.8.1 does not. The stored `national-v1.json` (77 regex-style rules) is
not a physical-key map and has no consumer.

## Evidence from the 0.8.1 audit

- The only transliteration table consumed at runtime is
  `crates/okkhor-transliterate/assets/avro-v1.json` (250 ordered regex rules),
  embedded at `crates/okkhor-transliterate/src/phonetic.rs:54` and compiled by
  `SuggestionEngine` at `crates/okkhor-engine/src/suggest/mod.rs:95`.
- `SuggestRequest` has no layout field (`suggest/mod.rs:41-47`). `encode_layout`
  in `okkhor-features` only produces a feature integer; it never selects a
  table. `SuggestionRequest.layout` is documented as metadata only.
- `layouts/phonetic-v1.json` (256 rules), `layouts/khipro-v1.json` (288 rules)
  and `layouts/national-v1.json` (77 mappings) are stored data with no
  `include_str!` consumer. Their own descriptions say "later engine task".
- There is no Probhat data at all, and no Bijoy *input* layout data:
  `encodings/bijoy-keyboard-v1.json` is explicitly reference-only. Bijoy in
  Okkhor means the SutonnyMJ *output encoding*, which does work.

## What must exist before a layout is advertised again

1. An ADR recording that `SuggestRequest` gains a real layout selector (or a
   separate fixed-layout path) and stating which suggestion stages are valid
   for a non-Avro table. The OKS1 roman→Bangla index is Avro-shaped, so it
   must not be applied blindly to another layout.
2. A loader that converts the stored `{key, output}` rule files into the
   ordered `{pattern, replacement}` format accepted by
   `PhoneticTransliterator::from_asset_json`, with a golden test per file and
   a rule-count check.
3. A per-layout engine selection in `DefaultEngine` with a fallback to Avro on
   any load failure, and a startup health event that reports the resolved
   layout without logging user text.
4. A Bijoy input layout asset derived from the exported reference data, with
   documented provenance and a golden corpus. Do not invent mappings.
5. Differential tests against the owner's reference installs, recorded as
   compatibility differences, not silent "improvements".
6. Only then: re-add layout entries to `layouts.list` and the UI fallback
   list, one at a time, each with a real-key QA row.

## Owner decision needed

Whether to spend 0.9 on a full per-layout engine (National/Jatiya first, then
Khipro/Phonetic, then a derived Bijoy input layout), or to keep Okkhor a
single-layout phonetic keyboard with a separate Bijoy output encoding. Both
are honest products; the current 0.8.1 state is the second one.
