## 2. `WTR1` is now a *fully specified* format (observed)

The format was previously "recognised by magic, no approved parser"
(`docs/parity/0.8-matrix.md:39-41`, `docs/design/suggestion-data.md:22-27`).
That is no longer true: the legacy app's own Python module `dic_bin_reader`
(PYZ entry, 9,283 marshalled bytes) carries a complete reader/writer docstring
for the same format, and `word_trie`'s `get_data()` docstring repeats the schema.
Verbatim (from the decompressed PYZ):

```text
File layout (identical to load_word_trie_bin / save_word_trie_bin in C):
    "WTR1" | u8 phonetic | 6 x pstr header
    filter  : u32 n, n x (pstr key, pstr value)
    value   : u32 n, n x (pstr alias, u32 m, m x pstr target)
    main    : u32 n, n x pstr            (n = 0 when phonetic)
    suffix  : u8 is_dict, dict(like filter) or list(u32 n, n x pstr)
    recent  : u32 0x31524652, u32 n, n x u32 index
              (index -> value_dic entry order if phonetic, else main_words order)
              the old format (u32 n, n x pstr) is also read
    unknown : u32 n, n x pstr
    pstr = u16 byte-length + UTF-8 bytes
```

with `header = {version, regEx, developer, name, github, comment}` and the
semantic note **`value_dic: {alias: [word, ...]} — first word = preferred`**, plus
`suffixes` order is "order kept = order applied" and `recent_known` holds
"aliases in phonetic files".

A structural parser written from this spec consumes all three files to the last
byte (`trailing 0` for 5,445,415 / 3,203,640 / 4,579,666 bytes), so the spec is
confirmed, not guessed. First two header offsets for `bangla_dict.bin`:
phonetic flag at `0x04`, header `pstr`s from `0x05`, `filter_dic` at `0x185`,
`value_dic` at `0x1BD`; magic `57 54 52 31` at `0x00`, version `31 2e 32` = `1.2`
at `0x07`.

### 2.1 Parsed contents (observed)

| Field | `bangla_dict.bin` | `NonPhonetic_dict.bin` | `English_dict.bin` |
| --- | ---: | ---: | ---: |

| `filter_dic` | 4 (`ড়→ড়`, `ঢ়→ঢ়`, `য়→য়`, `ব়→র`) | 4 (same) | 0 |
| `value_dic` aliases | **135,425** | 0 | 2 (`plz→please`, `bd→Bangladesh`) |
| `value_dic` targets | **151,126** | 0 | 2 |
| multi-target aliases | **13,192** (28,893 targets) | 0 | 0 |
| targets/alias max | 12 | – | 1 |
| `main_words` | 0 | **137,344** | **406,861** |
| `suffixes` | **142** (`ই→i` …), dict, order significant | 142, list | 0 |
| `recent_known` | **555** indices | **1,211** indices | **1,701** indices |
| `recent_unknown` | **271** words | 2 | 500 |

Consequences that matter for 0.10.0:

1. **There is no frequency field anywhere.** `value_dic` is `alias → ordered
   target list`; order is the only preference signal. `recent_known` is an
   ordered MRU list of indices, not counts. Any claim that the legacy dictionary
   carries frequencies is false.
2. **`recent_known`/`recent_unknown` are the packager's personal state**
   (e.g. `একটা`, `ইন্টারেস্টিং`, `তুমি`, `আমার`, and misspellings such as
   `thei`, `wiht`, `wehn`). They are **user data**, not dictionary data: import
   counts only, or skip. Never ship them.
3. **`filter_dic` is a normalisation table** applied at load (decomposed nukta →
   precomposed). It is the missing step in our importer (§3).
4. The English list is large (406,861) but unfiltered — it opens with `Ex`,
   `Ez`, `Fu`, `ac`, `ad` and contains `aaberg`, `aahed`, `aahing`. Coverage,
   not quality.

### 2.2 `STRI` sentence history (observed)

```text
"STRI" | u32 version=1 | u64 max_sentences | u64 sentence_count
per sentence: u64 byte_length | UTF-8 bytes   (newest first)
```

Bangla: 308 sentences, max 1500; English: 304, max 1500. The payload is
**plaintext UTF-8 user sentences** (`এখন আখন …`, `i am wanting to buy a portable
monitor …`) — readable without any key. That is a privacy finding in its own
right and an argument for our DPAPI-encrypted `learning.bin`.

`SentenceTrie.py` (PYZ) wraps `_sentencetrie_native.dll` and documents the
runtime: `suggest_next_word(word, top_n=5)` and
`suggest_next_word_for_partial_sentence(partial, top_n=5)` over word transitions
the C side rebuilds on load; `max_sentences` is the only tunable; `compact()`
drops unreferenced vocabulary. So legacy next-word = **bigram-only, capped at
1,500 sentences**, no trigram, no frequency weighting.

## 3. What our importer actually keeps — and why it loses 15.7 %

Observed by re-parsing both artifacts and diffing them.

| Metric | Value |
| --- | ---: |
| Kontho aliases | 135,425 |
| OKS1 `ROMAN` rows | 114,193 |
| Aliases missing from OKS1 | **21,232 (15.7 %)** |
| Kontho target strings | 151,126 |
| Targets reachable through OKS1 | 114,193 (75.6 %) |
| Kontho multi-target aliases | 13,192 |
| Multi-target aliases with >1 value in OKS1 | **0** |

Root causes (exhaustive; each alias classified once):

| Cause | Aliases | Example |
| --- | ---: | --- |
| Target fails NFC (decomposed nukta: `য+়`, `ড+়`, `ঢ+়`) | **21,204** | `ay → আয়`, `jor → জড়`, `hy → হয়` |
| Key not `[a-z]{1,24}` | 16 | `c:`, `oho:roh`, `du:sahos` |
| Target first char outside Bengali `Lo` | 12 | `a → া`, `i → ী`, `e → ে` (matras as first char) |

Mechanism, in our code:

- `scripts/build-suggestion-index.py:176-196` walks the byte stream and accepts
  one `(u16 key_len, ASCII key, u32 m, u16 value_len, value)` record. That
  `u32` is **`m` = number of targets**, not a frequency (`:180` treats it as
  `frequency`).
- `:163-170` states the importer "does not reconstruct the trie"; in reality it
  is reading `value_dic` correctly but only the **first** target of each alias,
  so `m > 1` aliases contribute exactly one row.
- `normalize_bangla` (`:72-87`) requires `unicodedata.normalize("NFC", text) == text`
  and rejects otherwise. Kontho stores many targets decomposed and relies on
  `filter_dic` at load; we never apply it, so 21,204 aliases vanish.
- `:220-221` gates on `100_000 <= len(rows) <= 160_000`, which passes today and
  would also pass after the fix, so the gate does not catch the loss.

Impact on the golden corpus (113 cases, `crates/okkhor-engine/tests/fixtures/suggestions/golden-v1.json`):

- 34 cases have a roman key that is **multi-target** in Kontho; we currently
  ship only the preferred target and cannot offer the alternatives at all.
  Examples: `bari → [বাড়ি, বারি, বাড়ী, বারী]`, `bon → [বন, বোন, বন্‌, বোন্‌]`,
  `ghor → [ঘর, ঘোর, ঘোর্‌, ঘোড়]`.
- 12 cases use keys Kontho does not have at all (`achhi`, `korcho`, `shundor`,
  `valobasha`, `raat`, `shomoy`, `bikale`, `rate`, `naam`, `porichoy`, `shu`,
  `apn`) — our Avro+wordfreq union is already broader there.
- 4 cases have a Kontho preferred target that is decomposed (`hoy → হয়`).

**Caution that shapes the plan:** Kontho's preference order is *not* authority.
`bon`'s preferred is `বন` while the corpus expects `বোন`; `cha → ছা` vs expected
`চা`; `bhat → ভাট` vs expected `ভাত`. So the order must be imported as a
**bounded, low-weight tie-break**, never as a hard override (see §8.2).

### 4.3 Ordering — the actual scoring constants (observed)

Decompiled from `word_trie.dll` (addresses are Ghidra entry points):

`calculate_similarity_score` @ `0x2aa8623b0` — Levenshtein over Unicode
codepoints (ASCII case-folded; conversion buffers cap at 127/129 codepoints):

```text
sim  = 1 - distance / max(len_a, len_b)
sim += 0.05   if len_a > 1 and len_b > 1 and first_codepoint equal
sim -= 0.03 * abs(len_a - len_b)
sim  = clamp(sim, 0, 1), rounded to 4 decimals
```

`suggest_similar_words.part.0` @ `0x2aa862690`:

```text
value path : skip candidates with abs(len_diff) >= 4, score vs converted text
alias path : score vs alias, keep only if score > 0.5, expand every target
final      : qsort desc, hard cap 16 results (0x7f8 bytes)
```

`get_rearranged_words.part.0` @ `0x2aa863160`:

```text
only for 3 <= len <= 11
for each adjacent swap i,i+1 that exists in the dictionary:
    score = 0.88 if i == 0 else 0.92        (0x3fec28f5…, 0x3fed70a3…)
dedupe by text
```

`suggest_split_words.part.0` @ `0x2aa8648e0`:

```text
coverage = min(1, sum(len(part)) / len(input))
score    = coverage * (0.75 or 0.95) - 0.03 * (parts - 1) - 0.12 * (single-char parts)
score    = max(0, round4(score));  0.95 unless a per-segment flag is set, then 0.75
```

`merge_candidate.part.0` @ `0x2aa861b60`: dedupe by `strcmp`, keep **max**
score, truncate the word at 127 bytes.

`suggest_word` @ `0x2aa868860`: `_strnicmp` prefix match over the alias table,
emit targets in stored order; when the English prefix is ≥ 2 chars and recents
are enabled, MRU recents are merged into the result, capped at
`min(recents_limit, 4)` (hard-coded 4 in the loop guard).

So legacy ranking is **lexicographic prefix order + fixed similarity heuristics +
recents membership**. No counts, no learning from acceptance, no context.

## 5. Bongo / `riti` comparison (observed)

Bongo's engine (`vendor\rust\riti`) is Avro-derived and ships JSON:

| File | Bytes | Contents |
| --- | ---: | --- |
| `data\dictionary.json` | 4,089,797 | object with **47 onset keys** (`d`, `k`, `b`, …); **159,426 words** total, 1 duplicate across keys |
| `data\suffix.json` | 22,894 | 737 `roman → Bangla` suffix pairs |
| `data\autocorrect.json` | 138,229 | 5,337 pairs (Avro-style roman autocorrect) |
| `data\Borno.json`, `National.json`, `Probhat.json` | ~6.9 KB each | layout maps |

159,426 matches our own Avro count (`mention of 159,426 raw` in the manifest), so
`dictionary.json` **is** Avro's 47-table word list, re-encoded. It carries no
counts; groups are approximately length-ordered but not strictly sorted
(`d` → `দ, দু, দংগল, দংশ, দংশক…`).

Ranking (`src\suggestion.rs`, `src\phonetic\suggestion.rs`):

- `Rank::First < Rank::Emoji < Rank::Other < Rank::Last` (`suggestion.rs:209-233`);
  `Other`/`Last` order by a `u8` rank.
- `Rank::new_suggestion(item, base)` uses `edit_distance(base, item) * 10`
  (`suggestion.rs:167-170`) — a 0–255 integer, not a calibrated score.
- `include_from_dictionary` sorts the onset list, then maps each word through
  `new_suggestion` (`phonetic/suggestion.rs:308-319`).
- User state is `user_autocorrect.json` plus
  `phonetic-candidate-selection.json` — **one selected output per roman word**
  (MRU), plus suffix composition (`get_prev_selection`, `:251-306`). Sticky
  selection, no counts, no acceptance rate.

Conclusion: **neither reference implementation has word frequency.** Kontho has
an authored preference order plus a tuned similarity/transposition/split scorer;
Bongo has edit distance over a length-ordered Avro list. Okkhor is already the
only one of the three with a frequency prior (`wordfreq` zipf).

| autocorrect | `autocorrect(roman)` → rules | `1.15 + zipf*0.05` else 1.10 | 0.90 | Transliteration |
| rule exact | transliterator output | `1.00 + zipf*0.08` else 0.84 | output confidence | Transliteration |
| rule prefix expansion | `prefix_bangla` | `(0.58 + zipf*0.28 - extra*0.01)` clamp 0.25–0.92 | 0.60 | Dictionary |
| vowel variant (`o`→`O`) | suffix `o` | `1.08 + zipf*0.05` else 0.90 | 0.90 | Transliteration |
| suffix | `longest_suffix` | `0.88 + zipf*0.05` else 0.70 | 0.50 | Transliteration |

`popularity(zipf) = zipf / 800` (`:554`). English completions are a separate
path: `0.50 + zipf*0.45 - extra*0.01` (`:278`).

### 6.3 Smriti wiring

- Model: `score = 1.00*base + 0.35*ln(1+user_freq) + 0.25*recency
  + 0.40*context + 0.30*acceptance - 0.50*correction + 0.20*phonetic
  + 0.60*ln(1+pair_freq)` — `crates/okkhor-learn/src/store.rs:528-536`, weights at
  `config.rs:20-33`, half-life 14 days at `config.rs:49`.
- Emitted today (only): `WordCommitted` (`apps/okkhor-daemon/src/main.rs:2839`,
  `:2860`, `:2868`), `TransliterationCommitted` (`:1163`, `:2889`,
  `apps/okkhor-daemon/src/words_store.rs:458`).
- **Not emitted anywhere:** `SuggestionShown`, `SuggestionAccepted`,
  `Correction`. Grep over `apps/okkhor-daemon/src` returns zero call sites. So in
  production `acceptance_rate` is always 0, `correction_rate` always 0, and the
  `shown` denominator never exists. `docs/learning.md:31-43` describes the
  signals; `AGENTS.md` already says accepted/correction learning is later work.
- Feature vector is frozen at 16 fields, `SCHEMA_VERSION = 1`
  (`crates/okkhor-features/src/lib.rs:45`, `:196-213`). Any new field is a schema
  bump plus a model retrain (§8.2 avoids that for 0.10.0).

## 8. 0.10.0 plan

### 8.1 Phase A — reviewed WTR1 exporter v2 (P0)

Replace the byte-stream heuristic in `scripts/build-suggestion-index.py` with a
bounds-checked parser of the documented layout, and change the index format:

```text
ROMAN v2 record:  u32 key_off | u16 key_len | u8 preferred_rank | u16 out_len | u32 out_off
                  (all targets of an alias become one row each, ordered by rank)
OKS1 v2:          version = 2, ROMAN record = 15 B, sort key = (key bytes, rank)
```

Rules:

1. Apply `filter_dic` (4 nukta mappings) **then** NFC; keep targets that are
   already NFC.
2. Accept every `m` target, not just `m == 1`; cap `m ≤ 16` (observed max 12).
3. Reject keys outside `[a-z]{1,24}` explicitly and count them in the manifest
   (`rejected_keys`), so the loss is visible instead of silent.
4. Keep the known-mapping assertion (`:203-219`) and add multi-target assertions:
   `bari`→4 rows with rank 0 = `বাড়ি`, `bon`→rank 0 = `বন`, `cha`→rank 0 = `ছা`
   (golden tests pin the *ranking effect*, not the legacy order).
5. `recent_known`/`recent_unknown` are **not** imported; record their counts in
   the manifest as `nms_packager_recents` (provenance without user data).
6. Optional, separately gated: `NonPhonetic_dict.bin` `main_words`
   (18,142 words not already in `BN`, all zipf 0) and `English_dict.bin`
   (357,363 new) behind `--include-nonphonetic` / `--include-english-bulk`.
   Budget: full pairs ≈ +1.0 MB, NonPhonetic ≈ +0.35 MB, English bulk ≈ +6 MB.

Acceptance metrics (Phase A):

| Metric | Target |
| --- | --- |
| `roman_keys` in manifest | ≥ 135,400 (from 114,193) |
| `roman_pairs` | ≥ 151,120 (from 114,193) |
| Multi-target aliases with ≥ 2 rows | = 13,192 |
| Golden top1 / top5 | **must not regress** (≥ 92.9 % / 100 %) |
| Index size | ≤ 11.5 MB (v2 with full pairs) |
| Loader validation | all `IndexError` paths still covered; v1 files rejected as `BadVersion` |

Cross-check: `scripts/import-legacy.ps1` already records the same SHA-256; the new
importer must reuse that digest and fail on drift.

### 8.2 Phase B — ranking signals and weights (P0/P1)

Constraint: **no `FeatureVectorV1` change in 0.10.0.** New dictionary-derived
signals are folded into `base_score` (the shipped logistic model reads
`base_score`, `phonetic_score` and the learned counters; it stays valid).
Schema v2 + retrain is 0.11 work and needs an ADR.

| # | Signal | Where | Value (first cut) | Gate to keep it |
| --- | --- | --- | --- | --- |
| 1 | Preferred rank | `stage_roman` | `score -= 0.015 * min(rank, 4)` capped −0.06 | only if golden top1 ≥ 92.9 % |
| 2 | Tie-break epsilon | sort tail in `Smriti::rank` | `-1e-4 * rank` | mandatory, cannot flip a real score |
| 3 | Transposition (typo) | new `stage_typo` | 0.86 for swap at 0, 0.90 otherwise; len 3–11; must exist in `BN` | top1 +≥ 1 case, p99 ≤ 2 ms |
| 4 | Fuzzy length guard | `stage_typo` / fuzzy | skip when `abs(len_diff) ≥ 4`, penalty −0.03/char | no worse than #3 alone |
| 5 | Compound split | new `stage_compound` | `0.60*coverage − 0.03*(k−1) − 0.12*singles − 0.15`, rows in a separate strip | only if a dedicated "join the words" case set exists |
| 6 | Freeze the shown/accepted clock | `SuggestRequest.at(now_ms)` per composition | one timestamp per composition | replay determinism |
| 7 | User pair preference | `Smriti.pair_frequency` (exists) | weight 0.60 (unchanged) | needs #3 of Phase C |

Deliberate non-goals for 0.10.0: trigrams, per-app context, ONNX tier 2,
per-word learned weights, auto-insert.

Guardrails copied from the legacy design where it is *sound*:

- cap the fuzzy pool at 16 candidates before the merge (Kontho does exactly this);
- merge by **max** score per text (Kontho `merge_candidate`), then sort;
- keep 2–5 exploration slots: rank 1–2 by score, positions 3–5 may differ by at
  most one score step (prevents feedback lock-in, `docs/learning.md:235`).

### 8.3 Phase C — user-learning event set (P0)

Emit the three missing events, with bounded shapes and per-composition dedupe.

```rust
SuggestionShown   { word, language, position: u8, request_id: u32, timestamp_ms }
SuggestionAccepted{ word, language, position: u8, roman_input, previous_word, timestamp_ms }
Correction        { from, to, language, position: u8, timestamp_ms }
NextWordAccepted  { previous_word, word, language, timestamp_ms }   // for the strip
```

Rules:

1. **One `SuggestionShown` per (request_id, position)** — the card repaints many
   times per keystroke (30 ms coalescing), so the emitter must dedupe against a
   bounded `HashSet<(u32, u8)>` of the current composition (≤ 10 entries) and
   flush on commit, dismiss, pause or word boundary.
2. `SuggestionAccepted` implies `shown += 1` only when the position was not
   already counted (no double counting, no negative acceptance).
3. `Correction` fires only on backspace/retype inside the same word slot before
   the next boundary; it also emits `WordCommitted{source: Correction}` for the
   replacement (`docs/learning.md:228-233`).
4. No event for password fields, while paused, or for Latin fallback commits
   (`docs/superpowers/plans/0.9-learning-and-next-word.md:31`).
5. Events go to the existing bounded queue → memory → 64-event/30 s batch →
   DPAPI `learning.bin`. The typing thread never touches disk.

Storage bounds (row caps exist in `docs/learning.md:240-249`; add byte caps):

| Table | Rows | Bytes/row (est) | Byte cap |
| --- | ---: | ---: | ---: |
| `words` | 50,000 | ~48 | 2.4 MB |
| `pairs` | 100,000 | ~80 | 8.0 MB |
| `bigrams` | 200,000 | ~40 | 8.0 MB |
| snapshot total | – | – | **24 MB**, compact to 70 % in `maintain()` |

Privacy invariants (must be tested): no word text in logs; no telemetry with
text; `export`/`delete`/`pause` remain one-action; the snapshot never contains
window titles or app names.

### 8.4 Phase D — replay, A/B, and dataset pipeline (P1)

1. **Replay schema 2** (`docs/design/replay.md:7-27`): add optional
   `shown_position`, `composed_at_ms`, `corrected_from`. Bump `schema` to 2,
   keep reading v1. This makes acceptance/correction replayable, which the
   current 240-case synthetic set cannot do (it has no learning evidence — hence
   the 0.7 hybrid tie).
2. **Metrics** (already implemented in `crates/okkhor-train/src/metrics.rs`):
   top1, top5, MRR, keystroke savings, acceptance rate, p50/p95/p99, with
   segments by language/layout/source.
3. **Gates for 0.10.0** (all must hold before the default ranker changes):

| Gate | Baseline | Required |
| --- | --- | --- |
| Golden top1 (113 cases) | 92.9 % | ≥ 94.0 % |
| Golden top5 | 100 % | = 100 % (no regression) |
| Replay MRR (synthetic 240) | current | ≥ baseline − 0.005 |
| Ranking p99 | ~0.2 ms (0.2 smoke) | ≤ 2 ms |
| Candidate p99 | budget 3 ms | ≤ 3 ms |
| Learning snapshot size | – | ≤ 24 MB after 30 days simulated |
| Acceptance-rate sanity | 0 | > 0 and monotone in replay |

4. **A/B**: `--ranker baseline|hybrid` already exists; add a third
   `--ranker v010` cohort and a settings flag. Beta channel first; rollback if
   top1 or p99 regresses; no text in telemetry, counters only.
5. **Dataset pipeline** (licensed/synthetic only, `docs/design/datasets.md`):
   - Frequency prior: Wikimedia `bn` dump → token counts → per-million →
     zipf-style buckets, replacing `wordfreq`-only popularity for BN. CC-BY-SA,
     derived counts only, attribution + legal review recorded (`:125`, `:140`).
   - Roman pairs: BanglaTLit (MIT) + Dakshina `bn` (CC-BY-SA) → train/eval pair
     preferences; synthetic romanisation of our own word list through all eight
     layouts for coverage.
   - Corrections: BanglaSEC (MIT) for correction candidates; evaluation only for
     the NC licences.
   - Every artifact gets a manifest (`schema 1`), checksum, row count, and a
     `train`/`eval` split by `case_id` hash. No raw user text, ever.
6. **GPU decision rule** (`uiu-h200`, H200 1g.18gb, per `AGENTS.md`): Tier 1 is
   16 features of logistic regression — CPU only. Use the GPU only if
   (a) a Tier 2 GBDT/MLP beats Tier 1 by ≥ 1.0 pt top-1 on a **licensed** holdout
   *and* (b) quantised inference stays ≤ 3 ms p99. Otherwise the GPU is not used
   for 0.10.0. A transformer next-word model is Tier 3 (idle only) and out of
   scope.

## 9. Risks and unknowns

| Risk | Mitigation |
| --- | --- |
| Kontho order is sometimes wrong (`bon`, `cha`, `bhat`) | weight ≤ 0.015/step, never a hard override; gate on golden top1 |
| Importing 406k English words dilutes ranking | bulk import off by default; measure coverage/quality split |
| `SuggestionShown` volume inflates the snapshot | per-composition dedupe + byte cap + 64-event batch |
| Acceptance learning creates a feedback loop | exploration slots 3–5, correction penalty, cap boosts |
| Legacy recents/recent_unknown are personal data | counts only in the manifest, never rows |
| Bigger index slows startup | startup validation is one pass; measure cold start (< 300 ms budget) |
| Model schema drift | no `FeatureVectorV1` change in 0.10.0; schema v2 is 0.11 + ADR |
| "Parity" overclaim | parity rows stay unsupported until the v2 parser is tested; update `docs/parity/0.8-matrix.md:39-41` only after A1 lands |

Unknowns that need an owner decision:

1. Do we keep Kontho's `preferred_rank` even when `wordfreq` disagrees? (Current
   recommendation: yes, but only as a ≤ 0.06 nudge and only for rank ≥ 1.)
2. Bulk English import: coverage vs noise. Needs a 500-case English completion
   set before deciding.
3. Compound split: valuable for Bangla, but it changes the card layout. Defer
   until the 0.9 next-word strip exists.
