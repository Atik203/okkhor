# Windows integration QA matrix — 0.2 input layer

Status: authored for milestone 0.2; execution pending.

This is the written pass/fail record for the 0.2 input layer. It covers the
behavior that unit tests cannot exercise: the global keyboard hook, focus, DPI,
IME, elevation, and session changes. It does not replace automated tests; see
[testing.md](../testing.md). The process, evidence rules, and privacy
constraints are in [the manual QA guide](README.md).

Related documents:

- [Architecture](../architecture.md)
- [Roadmap](../roadmap.md)
- [Performance](../performance.md)
- [Security and privacy](../security-privacy.md)
- [Release process](../release.md)

## How to use this matrix

1. Read [the manual QA guide](README.md) and prepare an isolated test account.
2. Copy the run header into the QA record for each environment.
3. Run every row on both `OS-A` and `OS-B` unless the row is explicitly tied to
   one build. A smoke test on one OS is not coverage for the other.
4. Fill in `Result`, `Evidence`, and `Notes` immediately. A row without evidence
   is not complete.
5. File a defect for every `FAIL` with the template at the end of this file.
6. Record accepted limitations in the limitation register. A limitation does
   not turn a failure into a pass unless the row's expected result names it.

Result values: `PASS`, `FAIL`, `BLOCKED`, `N/A`, `PENDING`. Definitions are in
[the manual QA guide](README.md#recording-results).

## Run sets and shorthand

| Name | Meaning |
| --- | --- |
| `OS-A` | Windows 11 24H2 x64, build 26100.x, latest cumulative update. Record the exact UBR from `winver`. |
| `OS-B` | Windows 11 25H2 x64, build 26200.x, latest cumulative update. Record the exact UBR from `winver`. |
| `BASE` | Test account with no personal data; MSVC release build from the commit under test; local session; normal user; single monitor at 100%; balanced power; no other keyboard hooks; Notepad available; clipboard cleared; synthetic fixtures only; evidence root configured. |
| `HARNESS` | Local 0.2 QA harness that can inject a fixture, force clipboard fallback, and keep the hook alive longer than `hook-demo`. It is not in this repository; see `LIM-01`. |
| `NONACT` | A launcher for `popup-demo` that does not change the foreground window. Confirm the foreground HWND before trusting placement evidence. |

Rows tagged `[harness]` cannot be completed with the 0.2 daemon alone. Rows
tagged `[demo]` use the existing `hook-demo` or `popup-demo`. Rows tagged
`[diagnostic]` are for investigation and never substitute for a release row.

A 0.2 candidate ships only when every box below is checked. The artifact,
signing, and rollback gates remain in [release.md](../release.md).

### Matrix completion

- [ ] Full matrix executed on `OS-A` and `OS-B`; exact builds, UBRs, and run IDs
      recorded.
- [ ] Every row passes, or its failure is triaged as P2 or P3 and accepted;
      no open P0 or P1 failure remains.
- [ ] Every `FAIL` has a defect with a repro, evidence, and either a fix or an
      accepted known limitation.
- [ ] Every `BLOCKED` row has an owner, reason, and accepted risk; no P0 or P1
      failure is accepted as permanently blocked.
- [ ] Flaky rows have three runs and a recorded pass rate.
- [ ] Evidence is sanitized, attached, and privacy-reviewed.

### Input behavior

- [ ] Hook installs, passes through, and stops cleanly on both OS builds.
- [ ] Pause hotkey toggles capture, is consumed by Windows, survives key repeat,
      and reports registration conflicts.

| Severity | Meaning | Release action |
| --- | --- | --- |
